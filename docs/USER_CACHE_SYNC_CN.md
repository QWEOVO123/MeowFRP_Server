# 用户信息 / DPI 的主动同步（控制协议 v3）

## 数据结构

不为每个用户建立独立物理表。使用一张多对多关联表 `user_node_cache`：
主键 `(user_id,node_id)` 查找用户的缓存持有者，反向索引 `(node_id,user_id)` 清理节点缓存关系。
节点授权表 `user_node_access` 也具有这两向索引，便于按节点、user_id 游标分页。

- `node_cache_sessions`：boot_id（进程启动编号）与 cache_session_id（本次缓存世代）。
- `identity_sync_sequence`：持久化递增版本，不使用服务器时间判断策略新旧。
- `desired_revision`：期望版本，兼任事务性待推送 outbox。
- `applied_revision`：边缘实际提交并 ACK 的版本。
- `cached_at`：对应完整用户数据实际提交后填写；准备、传输片段、写入进度不算“已缓存”。

用户删除后仍保留旧持有者，直到收到删除 ACK；删除节点在事务中清理其关系和会话。
SQL 保持 MySQL 5.7 兼容；升级会自动创建新表/索引，需要相应数据库权限。

## 断线、重连、重启

1. 边缘检测控制流断开后立即关闭新会话准入，取消并等待旧会话的数据应用和接收工作结束。
2. 在 SQLite 事务中废弃全部用户、Token、资源、端口授权、DPI 缓存及上次同步版本；失败不宣称清空成功。
3. 新 mTLS 流发送 hello（boot_id、cache_protocol=3）。中心根据证书验证节点身份，返回新 cache_session_id。
4. 边缘针对该世代再次确认清理事务成功，然后发送 cache_cleared。不是每个心跳都发送。
5. 中心收到对应世代的清空报告后，才在事务中删除该节点的全部 user_node_cache 记录并更新 node_cache_sessions。
6. 中心分页重建基线，边缘逐批提交，中心逐批确认实际缓存持有者。旧连接、旧世代、错误版本的 ACK 不被接纳。
7. 最后一批带 baseline_end，边缘完成全局权限核对并 ACK，中心回 sync_complete=true，节点才允许新登录/新租约。

中心重启、边缘重启、网络断线导致的重连均走上述流程。不依赖旧硬盘用户缓存。
普通 edgestate.Open 不清库；只有启动及控制客户端明确调用清理方法才会废弃缓存。

清理范围：
- 重连只废弃身份缓存，不删除节点配置、证书、未确认事件、命令去重、客户端本地封禁、节点本地 IP 封禁、运行时租约。
- 进程重启还清理旧运行时租约/隧道分配、重置旧在线状态，避免把上一个进程当成仍在运行。
- 活跃租约的 lease_issuers 指纹属于租约签发元数据，不用于恢复用户缓存或账号鉴权；用于重新同步后识别断线期间的 Token 轮换。
- 没有删除服务器上的数据库文件，也不能通过删除整个 edge-state.db 来升级。

## 分页、片段与进度

- 基线按 user_id 升序游标分页，每批最多 64 个获授权用户，仅查询本批关联的 Token/资源/端口授权/DPI，不再读取全部用户与全部 Token 后发送一个巨包。
- 每批都带独立递增版本，边缘不在后续基线批次重复删除前面已经提交的数据。
- 每批序列化后再拆成 512 KiB 原始数据片段；JSON 中的 Base64 片段约 683 KiB，低于原有 32 MiB gRPC 上限。单个用户数据超过 32 MiB 也不会变成一条超限消息。
- 每节点每次只发送一个未确认片段，下一片段收到传输 ACK 后再发送；只在整批提交 ACK 后确认缓存持有者。最后结束标志不会被中间片段 ACK 替代。
- 片段 ACK、已完成的 SQL 操作/租约核对进度刷新同步进度时间。普通心跳只保活，不掩盖卡死。
- 同步按连续 120 秒无进展超时，不再限制整份基线必须在 30 秒内完成。计时在实际发送片段时启动/更新，持续推进的基线可以运行超过 120 秒。
- MySQL 清理/确认、SQLite 应用、手动遥测读取/远程命令各有独立工作线程，不阻塞控制流正常心跳接收。
- 单批数据库准备仍有 20 秒操作超时；真正阻塞的 SQL、内存不足、磁盘满、证书/网络故障仍需运维处理，分片不等于无限资源保证。

## 主动更新与一致性

业务修改与待推送记录在同一 MySQL 事务中提交：
用户 DPI/资源策略、节点授权、用户状态、Token 创建/轮换/状态、端口授权、用户删除。
通知目标为“已有持有者”与“新获授权节点”的并集。节点没有用户时下发完整用户信息，不发依赖旧缓存的局部字段补丁。

工作线程收到修改通知立即推送；每两秒只检查中心本地待同步索引补漏，不向边缘轮询用户数据。
单次增量最多 64 个用户，SQLite 事务只替换本批用户。基线进行中的新修改仍留在 outbox，基线 ACK 后继续投递，不因批次/旧 ACK 而丢失。
全局 IP 封禁单独同步，不因新增用户或修改 IP 封禁而把全部节点用户缓存重新清空。

API 级修改、每批快照读取与 ACK 元数据操作共享一致性锁；不在网络传输或边缘落盘期间占用该锁。
直接在 SQL 控制台改业务表不触发通知，请使用 Web/API。中心重启后基线会重新读取完整最新数据。

## 可用性与安全边界

按要求彻底清空用户缓存，意味着重同步窗口不能继续用旧用户数据鉴权：
新登录/租约暂时返回可重试 503，状态沿用 edge_controller_disconnected，原因明确包含“正在同步”。
客户端心跳在缓存废弃期间也返回 503，不把缓存为空误报为“Token 无效”，不由该 HTTP 响应主动注销用户。

DPI 未完成基线时使用明确的同步中状态，不能因为缓存为空退回默认 allow-all。
已运行的 frpc 不会被本次清理函数主动停止，但新的 FRP 工作连接/运行时校验或待检查流量可能暂时被拒绝，部分业务连接需等待同步后重连。
本次不是“断线后用旧策略无限离线服务”的实现；彻底废弃旧缓存与完全无缝离线鉴权不能同时保证。

同步结束后核对所有运行时租约；用户失去权限、禁用、Token 轮换/失效会撤销对应租约并终止相关业务连接。
保留现有 FRP TCP 头部最多 8 KiB 的 DPI 采样机制，不把缓存已同步误称为所有旧流量已重新检查。

## 状态与日志

用户弹窗 / DPI 页面可手动刷新同步状态：
`GET /api/v1/admin/users/{id}/cache-nodes` 返回中心数据库记录，不强制上传边缘遥测。

关键日志：
- 边缘 `edge cache discard committed`：本地清空已提交。
- 边缘 `edge cache cleared ... reporting committed reset`：带新世代上报。
- 中心 `edge cache cleared ... center associations reset after edge commit`：中心关联清理已完成。
- 中心 `identity paged push ... baseline/end/users/fragments/bytes`：批次信息，不打印 Token 内容。
- 中心 `identity applied`：实际落盘 ACK 已确认。
- 边缘 `identity synchronization confirmed ... sync_complete=true`：最终允许新登录。
- 连续无同步进展会关闭流并重连；心跳丢失仍按原保活超时处理。

## 部署与验证

先升级中心，再升级全部边缘；均使用相同新版服务端二进制、保留各自 cfg/证书/数据库。
Qt 客户端和 frpc 不需要升级，FRP TLS 默认及现有连接参数不改变。
协议 v2/更旧节点仍走旧兼容全量格式，不具备 v3 分片/清空确认保障，不能用仅升级中心代替完整升级。

本轮完成 Linux/Windows amd64 构建、Go 静态检查；不运行自动测试、不启动服务、不访问远程 MySQL/服务器。
